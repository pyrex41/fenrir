## 1. Release milestones

Functional alpha ships a direct ARM64 compiler that takes the same .fen source to a native macOS executable and a Solo5 guest. The guest runs under spt in an ARM64 Linux VM on Apple Silicon. A second engineer must be able to install the release, modify an application, build and run both targets, diagnose a native trap, and replay a recorded failure from the published instructions.

High-performance alpha requires the same release to pass the functional gates and the performance scorecard below. Rust joins Nim as a systems-performance reference across all four applications. Elixir and Erlang are references for concurrent HTTP serving, supervision, durable work, and recovery. The existing Erlang supervisor also serves as a shared component in controlled comparisons. Benchmark results must identify which parts of each system execute in which language.

## 4. Performance gates and measurement

- Native Mac kernels. Score proof search, certificate checking, HTTP parsing/routing, and framed-log processing equally. Divide Fenrir elapsed time by the fastest eligible pinned implementation for each kernel, including Rust. Require geometric mean ≤1.5× and every kernel ≤2.0×. Report every language’s result alongside the ratio, with output verification and work counts. [Shen/JIT](https://github.com/tizoc/shen-jit) · [Koka](https://github.com/koka-lang/koka) · [Nim memory managers](https://nim-lang.org/docs/mm.html)
- Solo5 kernels. Compile each kernel as an ARM64 guest and compare it with an optimized C guest using the same tender, device setup, input transfer, and timing boundaries. Apply the same 1.5× mean and 2.0× individual thresholds. Keep Rust, Nim, Koka, Shen/JIT, Elixir, and Erlang host timings labeled by execution environment. Alpha does not require porting those runtimes to Solo5.
- Services. For each Fenrir target, require ≥⅔ of the fastest matched reference’s sustainable throughput and p99 ≤1.5× that reference at 70% of the slower system’s measured capacity. Select the throughput reference once and use that same implementation for the latency comparison. On Solo5 use a matched guest behind the same ingress and storage path. Define sustainable capacity as ten minutes without growing backlog, fewer than 0.1% unexpected errors, and zero invalid histories. Report idiomatic Elixir/BEAM deployment results alongside the matched runs, including overload and recovery.
- Memory and experimental quality. Require peak memory ≤2× the matched speed reference on each single-process kernel. For services publish guest, VM, BEAM, and storage memory separately with the measurement method. Use one identified Apple Silicon machine, fixed resource budgets, rotated execution order, and at least ten paired samples. Separate compilation, VM or process startup, warm-up, and steady execution. Publish raw timings and paired 95% confidence intervals. Rerun inconclusive rows. An output mismatch invalidates the timing.
- Optimization sequence. Start with profiles from the four applications. Prioritize measured costs in boxing, copying, allocation, closure calls, handler dispatch, continuation frames, and register allocation. Accept an optimization only after rechecking the affected semantic fixtures and the full scorecard. Track cold-start and recovery independently of warm throughput.

### Prover representation experiment

Prioritize a three-way Solo5 comparison before further instruction selection work. Run compact C, a second C prover using pointer-linked formulas and Fenrir’s persistent queue with the same append and branch-sharing rules, and the Fenrir prover. Use the same corpus, certificates, search budgets, timed entry point, optimization level for the C programs, tender and guest CPU allocation. Verify traversal order, remaining fuel, exact proof or model, and rejection of mutated certificates. Count queue cells constructed and copied in an untimed diagnostic. State how formula initialization, proof byte construction, atom-set operations and reclamation differ. A C persistent queue backed by an arena would measure queue-copy and layout costs under that allocation policy.

For search and checking separately, publish elapsed times and peak memory for all three. Compare the persistent C guest with compact C, then compare Fenrir with persistent C. As an exploratory statistic, when Fenrir takes longer than compact C, report the fraction of the elapsed-time gap reproduced in C as (persistent C − compact C) / (Fenrir − compact C), computed on matched blocks. Retain negative values and values over one. If the denominator is near measurement noise, use the raw paired differences. A substantial reproducible shift toward Fenrir supports prioritizing data representation. A small shift directs the next experiment toward costs still unmatched, including allocation, proof bytes, generated code and runtime. The compact C guest remains the release reference.

A later pass could make allocation points and live pointer roots explicit before frame layout. Its verifier would check that every live managed pointer has a root at each collecting call and that raw I64 slots are excluded.
